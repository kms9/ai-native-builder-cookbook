# 第 4A 章｜先把 AI 放回真实业务世界

第 4 章那次重复写入事故停住以后，澄川工业没有马上讨论换模型。

销售负责人关心的是客户跟进有没有失真；销售运营关心 CRM 字段和责任人是否还能相信；产品负责人追问“当前产品能力”到底由哪份资料说了算；IT 则要确认哪个系统拥有最终写入权。几个人讨论的是同一场事故，却分别站在流程、数据、知识和系统边界上。

这时项目组才意识到，“客户跟进助手”并不是一个孤立的软件功能。它插进了一条已经存在的业务链：客户会议结束，销售判断需求，核对公司能够承诺什么，更新商机状态，安排下一步，并在必要时把问题交给售前、产品或审批人。

如果只画一张 Agent 架构图，这条链会被压成“模型调用几个工具”。系统看起来更简单，真正决定成败的责任却消失了。

这一章先不讨论怎样实现。我们要把 AI 放回组织原本就有的业务结构里，分清业务结果、能力、决策、流程、角色和系统各自回答什么问题。后面的知识、Ontology、Workflow 和 Agent 才有落点。

## 企业不是一组等待 AI 调用的 API

站在工程接口上看，澄川有会议系统、知识库、CRM 和任务服务。站在业务上看，这些系统只是承载物。

销售真正要完成的是另一件事：在一次客户会议之后，把尚未结构化的信息转成可信的下一步，并让后续人员知道发生了什么、依据是什么、谁需要行动。

这项工作至少经过五个判断：

1. 客户到底表达了什么；
2. 哪些说法只是条件、设想或长期目标；
3. 公司目前能确认什么产品事实；
4. 哪些内容应该进入 CRM，哪些应当保持待确认；
5. 下一步由谁负责，是否需要升级或审批。

其中只有一部分适合交给模型。其余部分可能属于既有规则、角色职责、产品资料治理、CRM 权限或人工决定。

所以 Builder 在看到接口之前，先要弄清楚一件事：**组织现在靠什么能力完成这个结果，问题究竟出在哪一段。**

## 从业务结果往下拆，而不是从“做一个 Agent”往上找理由

澄川最初的需求是“做一个销售 Agent”。这个说法给出了方案，却没有给出业务终点。

项目组后来把它改成一个更可检查的结果：

> 客户会议结束后，销售能够在可信依据下完成必要的内部记录和下一步安排；不把条件性表达改写成确定承诺，不让未经确认的内容改变高影响业务状态。

有了这个结果，团队才开始往下拆。

| 层次 | 澄川要回答的问题 | 当前例子 |
|---|---|---|
| 业务结果 | 什么变化才算有价值 | 会后记录更快、更完整，同时不增加错误承诺 |
| 业务能力 | 组织必须会做什么 | 识别客户需求、核对产品依据、维护商机记录、安排下一步 |
| 业务决策 | 哪些地方需要作出判断 | 这句话是不是当前需求；这条资料能不能支持建议；这个字段能不能提交 |
| 流程 | 工作按什么顺序和条件推进 | 会议结束 → 核对依据 → 准备变更 → 销售确认 → 写入 |
| 角色与责任 | 谁拥有判断权、维护权和批准权 | 销售、内容负责人、CRM 管理员、技术负责人 |
| 系统 | 哪些数字能力承载这些工作 | 会议系统、批准资料目录、CRM、工作流服务 |

这张表不是企业架构的完整方法，也不要求项目先做一轮大型建模。它的作用只是防止几个常见错位：把接口当能力，把字段当业务语义，把模型输出当决定，把“能调用”当“有权执行”。

[The Open Group 对 TOGAF 的介绍](https://www.opengroup.org/togaf)把 Enterprise Architecture 作为一套支持组织设计和变化的方法，而不是单纯的 IT 系统清单。对 AI Native Builder 来说，真正有用的是这种视角：先看组织想改变什么，再决定业务、数据、应用和技术分别要承担什么变化。

## Business Capability 让团队先谈“必须会什么”

流程会变化，组织结构会调整，系统也会替换，但一些能力会长期存在。

澄川今天用 CRM A，明年可能迁移到 CRM B；客户会议也可能从线上变成现场。但“维护可信客户记录”仍然是一项业务能力，“核对产品承诺依据”也是。

能力视角可以帮助团队避免过早绑定实现。

例如：

```text
客户跟进
├─ 理解客户表达
├─ 核对产品与商务依据
├─ 形成内部记录
├─ 安排下一步责任
└─ 管理需要升级的例外
```

其中“理解客户表达”可能需要模型；“当前产品资料是否有效”应优先由版本和发布规则判断；“提交 CRM 变更”应由受限动作完成；“价格例外是否批准”仍由已有审批流程负责。

如果把这些都塞进一个“销售 Agent”，系统边界会迅速变得含糊。能力拆开以后，团队反而更容易判断哪些地方值得引入 AI，哪些地方应该保持确定性。

## Decision 比页面和步骤更接近 AI 的作用点

AI 很少真正替代一整条业务流程。它更常介入流程中的某些判断。

澄川会后处理里，以下几个判断性质并不相同：

- “这段话提到了接口人名单”是信息识别；
- “客户已经承诺下周提供名单”是事实判断；
- “这条信息应该写进 `next_action`”是业务语义映射；
- “现在允许提交这项变更”是权限与状态判断；
- “是否修改预计成交日期”是高影响业务决定。

前几项可能适合让模型参与，后两项则不能因为模型更强就自动获得决定权。

Builder 因此要把“哪里用 AI”改写为：**哪个 Decision 需要模型参与，模型提供什么证据或建议，最终决定由谁或什么规则作出。**

这一步会直接影响后面的设计。如果模型只负责从会议中提取候选事实，那么它需要的是会议上下文和输出结构；如果它还要判断资料是否足够，就需要来源版本和冲突规则；如果它能提交动作，就必须再加审批、权限、状态和恢复机制。

## 流程不是业务世界本身

画流程图很容易让人产生一种错觉：只要步骤顺序清楚，业务就已经被理解了。

但澄川的事故并不是“先检索还是先生成”的顺序问题。真正出错的是几个业务概念没有被约束：

- “尽快”在什么条件下能变成日期；
- 哪份产品资料代表当前有效口径；
- 一个字段建议是模型猜测、销售草稿，还是已批准变更；
- 同一商机在预览和提交之间发生变化后，原建议是否仍有效。

这些问题需要对象、关系、规则、身份和状态，而不仅是箭头。

因此，本书后面会一直保持一个区分：

> 流程描述工作怎样发生；业务语义说明流程中处理的东西到底是什么。

第 6 章会重构工作流，第 7 章会把对象和状态落成系统契约。在此之前，第 4B 章先解决更基础的问题：AI 怎样知道会议、商机、产品资料、客户需求和审批之间是什么关系。

## 四个架构域只用来防止漏问题

企业架构里常见 Business、Data、Application、Technology 四个视角。这里不把它们当成新的考试术语，而把它们当成四组检查问题。

### Business：为什么做，谁承担结果

澄川要改善的是客户会后的内部跟进，不是“提高大模型使用率”。业务负责人要说明目标、边界、价值和不能牺牲的风险底线。

### Data / Knowledge：系统根据什么知道事实

会议转写、产品资料、CRM 记录分别代表什么，谁维护，什么时候失效，发生冲突怎么办。这里既有数据问题，也有知识和语义问题。

### Application：哪些能力由什么组件承担

哪些步骤属于已有 CRM，哪些属于确定性工作流，哪些需要模型，哪些动作需要人工确认。Agent 在这里是一种应用能力，不是凌驾于所有系统之上的“总脑”。

### Technology：这些能力怎样可靠运行

身份、网络、模型服务、运行时、队列、日志、状态存储、隔离、监控和恢复都落在这里。技术底座决定系统能不能稳定执行，但不会替团队定义业务含义。

四个视角连起来后，问题会更清楚：

```text
业务结果与责任
      ↓
数据、知识与业务语义
      ↓
应用、Workflow 与 Agent 能力
      ↓
Runtime、集成与基础设施
```

箭头不是单向交付。技术限制可能迫使流程收缩，试点中的失败也会暴露业务规则和知识资产的问题。Builder 要做的是让这些变化能够互相追溯，而不是维护四份互不相干的架构图。

## 澄川项目先留下五个上层问题

事故复盘结束时，项目组没有写“升级到更强模型”，而是在项目记录里留下五个问题：

1. 当前试点究竟服务哪项业务结果；
2. 哪些业务能力需要改善，哪些已有能力不能被破坏；
3. 模型参与的是哪些 Decision，而不是笼统地“负责客户跟进”；
4. 这些 Decision 依赖哪些可信对象、关系和依据；
5. 哪些动作必须由规则、审批和系统权限控制。

这五个问题把讨论从 Agent 功能拉回了业务世界。
