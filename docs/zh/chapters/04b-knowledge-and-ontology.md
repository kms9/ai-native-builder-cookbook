# 第 4B 章｜让 AI 读懂同一个业务世界

澄川事故里有一句话反复出现在复盘记录中：“预算批准后尽快推进。”

销售听见的是一个有前提的客户意向；模型把它压成了一个时间信号；CRM 里却需要一个结构化字段。三者都在处理同一句话，含义却不一样。

另一处问题更隐蔽。会议里客户询问某项接口能力，知识库里同时搜到 v2.1 和 v2.3 两份产品说明。两份文档都写得像正式资料，但 v2.1 已经失效。若系统只做相似度检索，模型可以找到“相关内容”，却不知道哪一份拥有当前解释权。

这说明企业里的 AI 不只是缺信息。很多时候，它缺的是一套共享的业务含义：什么东西是同一个对象，哪些关系成立，谁能证明什么，哪个版本有效，哪些动作可以改变状态。

这一章从企业知识管理往前走一步，解释为什么文档、RAG、领域模型和 Operational Ontology 不是同一个东西，以及它们怎样共同支持后面的 Workflow 和 Agent。

## 文档很多，不等于组织知识已经可用

澄川已经有会议转写、产品资料、CRM 记录、销售手册和审批说明。项目组最初把这些材料都接进检索，效果却没有想象中稳定。

原因并不神秘。文档解决的是“内容被保存在哪里”，而业务判断还需要回答更多问题：

- 这份资料由谁负责；
- 当前是否有效；
- 它能证明什么，不能证明什么；
- 它和哪个客户、产品、商机或会议有关；
- 两份资料冲突时谁优先；
- 某个事实在什么时间范围内成立。

如果这些信息只存在于熟练员工脑中，RAG 只能把文字拿给模型，无法把组织已经形成的判断规则一起交过去。

所以企业知识管理的目标不只是“让 AI 搜得到”，还要让人和系统知道一条知识的身份、责任、版本、适用范围和来源。

澄川后来把批准产品资料登记成知识资产。每项资产至少有名称、负责人、版本、生效日期、失效条件、适用产品和访问范围。检索仍然存在，但检索对象从“整个共享盘里的相似文本”变成了“当前任务允许使用的有效知识资产”。

## Taxonomy 解决找东西，Ontology 解决理解和行动

团队很容易把分类体系和 Ontology 混在一起。

分类体系首先解决组织和检索。澄川可以按产品线、客户行业、资料类型、地区和生效状态给文档打标签。这样做能明显改善查找，却仍然没有回答“客户需求”和“产品能力”之间是什么关系。

Ontology 关心的是另一层问题：这个业务世界里有哪些对象，它们怎样关联，哪些规则可以基于这些关系计算，哪些动作能够合法地改变状态。

可以先用一个简单对照理解：

| 层次 | 主要问题 | 澄川例子 |
|---|---|---|
| 知识资产 | 哪些内容值得长期维护 | 产品能力说明 v2.3、CRM 字段规则 |
| Taxonomy / Metadata | 怎样分类、过滤和找到 | 产品线、资料类型、生效状态、负责人 |
| 领域模型 | 业务里有哪些核心概念 | Customer、Opportunity、Meeting、ProductCapability |
| Ontology | 对象如何连接、判断和行动 | Meeting 关联 Opportunity；Evidence 支撑 Suggestion；Approval 允许 ChangeSet 提交 |
| Provenance | 这条结论从哪里来、经过什么过程 | 建议来自 M-082 片段和产品资料 v2.3，经销售 A-017 确认 |

这些层次可以由不同技术实现。小项目完全可以先用数据库表、配置和服务代码表达，不需要为了叫 Ontology 就先上图数据库、RDF 或某个专用平台。

## 领域模型先让团队说同一种业务语言

澄川最初的代码和文档里同时出现“客户”“公司”“账号”“商机客户”四种说法。销售觉得它们差不多，CRM 管理员却知道它们指向不同实体。

团队先从最小领域模型开始，给首个试点定义七个对象：

- `CustomerAccount`：CRM 中具有稳定身份的客户组织；
- `Opportunity`：一次具体销售机会；
- `MeetingRecord`：与某次客户会议及其转写版本绑定的记录；
- `ProductCapability`：当前有效的产品能力声明；
- `EvidenceRef`：指向原始来源和位置的证据引用；
- `CRMChangeSet`：等待审阅的一组 CRM 变更；
- `Approval`：有身份、有时间、有范围的人工决定。

对象名称不是重点，稳定身份才是。

例如同一客户可以参加多次会议，也可以拥有多个商机。系统不能因为会议里都出现“远航集团”，就把所有记录并到同一个 Opportunity。`MeetingRecord` 必须通过已经确认的关联指向 `Opportunity`，而不是由模型根据名称自行猜测。

关系开始稳定以后，很多“提示词问题”自然变成了系统问题：

```text
CustomerAccount
  └─ has → Opportunity
          └─ discussed_in → MeetingRecord

ProductCapability
  └─ evidenced_by → KnowledgeAsset

CRMChangeSet
  ├─ targets → Opportunity
  ├─ contains → FieldSuggestion
  └─ approved_by → Approval

FieldSuggestion
  └─ supported_by → EvidenceRef
```

这张关系图的价值不在画得漂亮，而在于它能让后面的检索、权限、评估和动作围绕同一套对象工作。

## Operational Ontology 多了“怎么判断”和“怎么改变”

只建对象和关系，还不足以支持真实行动。

澄川还需要回答：某条建议有没有足够依据，当前资料是否有效，变更单能不能提交，哪个角色有权批准。这里开始出现规则、函数、动作和权限。

[Palantir 对 Ontology 的公开介绍](https://www.palantir.com/docs/foundry/ontology/overview)把对象、属性、关系等语义元素，与 Action、Function 和动态安全等可运作元素放在同一层；它的另一份说明把一次 operational decision 拆成 Data、Logic、Action 与 Security。这里不照搬某个平台实现，但这种划分很适合澄川的问题。

澄川可以把当前试点写成四部分：

### Data：现在知道什么

例如会议 `M-082`、商机 `OP-314`、产品资料 v2.3，以及 CRM 当前记录版本 42。

### Logic：怎样判断

例如：

- `IsKnowledgeAssetEffective(asset, at_time)`：资料在当前时间是否有效；
- `IsSuggestionSupported(suggestion)`：建议是否拥有允许来源；
- `CanCommitChangeSet(change_set)`：审批、版本、字段白名单和环境是否同时满足。

这些规则能确定的部分应由代码和数据约束实现，而不是每次交给模型重新理解。

### Action：怎样改变业务状态

例如：

- `ProposeCRMChange`：创建一份待审阅的变更单；
- `ApproveCRMChange`：记录销售对指定内容的批准；
- `CommitCRMChange`：在版本和权限检查通过后提交变更。

动作名称应该表达业务意图，而不是暴露底层 `POST /crm/update`。

### Security：谁能看、谁能做

会议内容只能在授权范围内读取；销售可以批准自己负责商机的变更；Agent 不能因为提示词里出现“直接写正式环境”就提升权限；正式环境写入也不能继承沙盒调试凭证。

到这里，Ontology 才从“数据模型”变成了可支撑运行的业务语义。

## Agent 应看到业务能力，不必知道每个系统细节

如果把 CRM、知识库和会议系统的底层 API 全部直接暴露给 Agent，模型必须同时理解技术接口和业务规则。

例如一个通用 `update_record(table, fields)` 工具在工程上很灵活，在业务上却几乎没有边界。模型需要自己判断改哪个对象、哪些字段能改、是否需要审批、版本冲突怎么办。

更稳的方式是先把这些规则收敛成业务能力：

```text
GetMeetingEvidence
GetEffectiveProductCapability
BuildCRMChangeSet
ApproveCRMChange
CommitApprovedCRMChange
ReconcileUnknownCommit
```

底层仍然可以调用多个 API，但 Agent 看到的是已经带有业务含义和约束的能力面。

第 7 章的对象契约和工具契约会把这些内容继续落到代码和状态机里。本章先保留一个原则：**工具接口越接近业务动作，越容易把权限、状态和评估一起做实。**

## Provenance 不是在答案后面贴一个链接

“有引用”不等于“可追溯”。

澄川的一条建议可能经历：会议原话 → 提取候选事实 → 关联产品资料 → 生成字段建议 → 销售修改 → 提交 CRM。最终值如果只保存一个文档 URL，团队无法知道中间发生了什么。

[W3C PROV](https://www.w3.org/TR/prov-overview/)把 provenance 描述为与某个数据或事物产生过程有关的实体、活动和参与者信息，用来帮助判断质量、可靠性和可信度。放到澄川，至少要能回答四个问题：

1. 这条值引用了哪些原始材料；
2. 哪个版本的工作流和模型产生了候选；
3. 人是否修改或批准过；
4. 最终哪个动作改变了哪个环境状态。

因此 `EvidenceRef` 和第 7、8 章的运行轨迹不是两套系统。前者负责业务事实的来源，后者负责一次执行怎样使用这些来源并产生结果。

## 时间也是业务语义的一部分

很多企业事实不是永远成立。

产品能力会更新，价格政策会过期，客户阶段会变化，人员权限也会调整。只存“当前值”会让历史执行无法解释。

澄川因此为关键对象保留时间信息：资料的生效与失效时间、CRM 读取时的记录版本、审批发生时间、运行使用的模型和工作流版本。系统不追求把所有数据做成复杂时态数据库，但至少要能解释“当时为什么这样判断”。

这也直接影响评估。今天的产品资料不能反过来证明上个月的建议正确；回归测试如果替换了知识版本，也要明确这是在测试新规则，而不是重现旧运行。

## 最小 Ontology 应该随着场景长出来

Ontology 很容易被做成一场范围无限的建模工程。

澄川没有先建立“企业统一客户本体”。首个试点只建与当前任务有关的对象、关系、规则和动作，并要求每项都能回答一个实际运行问题。

一项内容只有满足至少一个条件，才进入首版模型：

- 用来识别当前任务处理的是谁或什么；
- 用来解释一条建议的业务含义；
- 用来决定某个状态或动作是否允许；
- 用来支持权限、审计或评估；
- 会被第二个流程稳定复用。

例如“客户所属城市”虽然是合法属性，但当前 CRM 四字段试点并不需要，就不必为了完整而加入。相反，`base_record_version` 看起来很技术，却直接决定变更单是否仍然有效，因此属于必须保留的业务运行语义。

## 到这里，RAG 的位置反而更清楚

RAG 仍然重要。澄川需要从会议和批准资料中找到与当前任务有关的片段。

但它现在位于一条更完整的链路中：

```text
知识资产
  ↓
分类、版本与权限
  ↓
领域对象与关系
  ↓
按任务检索证据
  ↓
规则与模型共同判断
  ↓
业务动作
  ↓
Provenance 与 Trace
```

检索解决“把什么材料带进来”，Ontology 解决“这些材料在业务世界里是什么意思”，Workflow 与 Agent 再决定“接下来做什么”。
