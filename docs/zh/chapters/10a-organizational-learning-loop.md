# 第 10A 章｜让每次执行反过来改进系统

澄川的系统已经经历过一次重复写入事故，也完成了两轮沙盒评估和一次第二团队复用。按普通项目习惯，团队现在可以把这些内容归档，进入维护期。

但项目负责人在复盘会上发现一个问题：大家已经积累了不少失败，却没有统一说明这些失败应该改到哪里。

资料冲突时，有人建议再写一段提示词；重复提交时，有人想给 Agent 增加“不要重试”的 Skill；渠道团队字段理解错误，又有人提出把更多说明塞进系统提示词。每次都能做出局部修补，系统却越来越难解释。

真正需要建立的不是“失败以后优化一下”，而是一条明确的学习路径：从运行证据里发现问题，判断问题属于哪一层，修改对应资产，再用回归证明修改没有破坏其他能力。

这一章补上这条闭环。

## Trace 先回答“发生了什么”，不急着回答“该改什么”

一次运行失败后，团队最容易直接看最终输出。

但澄川的 `T-018` 不是一句文案写错。系统先提交 CRM，接口超时；随后状态查询再次超时；变更单进入 `unknown`；界面却重新开放提交；用户第二次点击后，前端生成了新的幂等键，最终产生重复任务。

若只保存最终页面，团队只能看到“两条任务”。有完整 Trace，才知道问题发生在哪个状态转换。

一条够用的运行轨迹至少要让团队复原：

- 本次任务使用了哪个工作流、模型和知识版本；
- 读取了哪些业务对象和 EvidenceRef；
- 模型给出了什么候选判断；
- 规则和权限检查返回什么；
- 调用了哪个 Tool / Action，参数摘要是什么；
- 人在什么时间批准、修改或拒绝；
- 状态如何转换；
- 最终环境实际发生了什么。

Trace 的第一职责是保留证据，不是把所有日志永久保存。第 8 章已经限制了敏感载荷和保留范围；这里继续沿用同样原则，只保留分析和审计真正需要的内容。

## 失败分类比“模型错了”更重要

团队把失败全部归为“AI 错误”，改进工作就会自然集中到 Prompt、模型和 Skill 上。

澄川后来建立了一张更具体的失败分类表。

| 失败类型 | 典型现象 | 首先检查的资产 |
|---|---|---|
| 知识缺口 | 没有当前有效资料，模型只能猜 | Knowledge Asset、Owner、Freshness |
| 业务语义缺口 | 不清楚对象身份、字段含义或关系 | Domain Model、Ontology、Object Contract |
| 规则缺口 | 已知边界没有被确定性执行 | Rule、Function、Invariant |
| 方法缺口 | 同类任务经常使用错误分析步骤 | Skill、Instruction、Example |
| 流程缺口 | 固定步骤顺序、审批点或异常分支不合理 | Workflow、SOP |
| 调度缺口 | 开放任务中下一步选择经常错误 | Agent Policy、Planner、Tool Selection |
| 工具缺口 | 参数、副作用、幂等或错误语义不清 | Tool / Action Contract |
| 运行时缺口 | 暂停、恢复、状态持久化或隔离失败 | Runtime、State、Recovery |
| 治理缺口 | 越权、日志泄露、责任不清 | Permission、Policy、Human Approval |
| 评估缺口 | 问题上线后才发现，测试没有覆盖 | Eval Dataset、Rubric、Gate |

一条失败可能同时涉及两层，但团队仍要找到主要因果链。分类不是为了给部门分锅，而是为了避免所有问题都回到同一个地方修。

## `T-018` 为什么不是一个 Skill 问题

重复写入事故很适合说明这个区别。

团队当然可以在 Skill 里加一句：“如果写入结果未知，不要重复提交。”模型也可能在下一次记住。

但真正的不变量是：**只要某个副作用的结果尚未协调，同一业务意图不得生成新的提交身份。**

这条规则应该落在状态机、幂等和 Action 服务端。界面和 Agent 都可以看到它，但都不能覆盖它。

因此 `T-018` 的修复链是：

```text
Trace 复原事故
  ↓
确认 unknown 状态出口错误
  ↓
修改 State / Action Contract
  ↓
界面同步收紧按钮行为
  ↓
把事故转换为历史回归样本
  ↓
重跑全部高风险路径
```

Skill 可以补充“怎样解释 unknown 状态、什么时候交给人工”，却不是主要安全边界。

这正是学习闭环的价值：改动回到拥有这条责任的资产，而不是回到最容易编辑的文件。

## 知识失败要回到知识供应链

另一个例子来自产品资料。

如果系统因为找不到当前接口能力说明而阻塞，正确做法不一定是调大检索范围。团队先要确认：这份知识是否应该存在，谁负责维护，当前版本是否被登记，为什么检索目录没有拿到它。

澄川把这类问题处理成一条知识补齐流程：

1. 运行记录产生 `KnowledgeGap`；
2. 内容负责人确认这个缺口是否真实影响业务任务；
3. 从产品专家或正式资料中补齐知识资产；
4. 补上 Owner、生效范围、版本和来源；
5. 更新相关 Ontology 关系或检索索引；
6. 增加能重现原缺口的评估任务；
7. 新版本通过后再进入运行环境。

这里最重要的是第二步。不是所有“模型没找到答案”都值得补知识。有些问题本来就不在当前业务范围，继续阻塞比扩张知识库更合理。

## 业务语义错误要改 Ontology，不只改示例

华南渠道团队复用时，把“风险备注”理解成经销商承诺，原销售团队却把它用来记录客户采购风险。

如果只在提示词里多放几个例子，模型可能暂时学会区分，两个团队的数据含义仍然混在一起。

团队最终把问题改到本地业务语义：渠道团队重新定义自己的对象、字段含义、适用场景和来源责任；共享核心只保留 `CRMChangeSet`、审批状态、未知写入和轨迹等跨团队稳定机制。

当一个错误反复表现为“同一个词在不同流程里代表不同东西”，它往往不是语言表达问题，而是上下文边界或 Ontology 没说清楚。

## Skill 适合沉淀被验证过的做事方法

并不是所有改进都应该下沉成规则。

假设评估发现，模型在分析会议记录时经常把“客户长期设想”当作“当前需求”。业务专家检查后发现，有一套稳定的分析顺序可以减少错误：先标记时态和条件词，再区分当前事实、未来意图和假设，最后才映射字段。

这套方法适合进入 Skill。

Skill 可以保存：

- 任务目标和适用范围；
- 推荐分析步骤；
- 常见反例；
- 如何调用已有业务能力；
- 什么情况下停止并升级；
- 已通过哪些评估版本。

它不应该复制当前产品资料全文，也不应该重新定义服务端权限。

从失败里提炼 Skill，本质上是在保存“怎样做更可靠”，而不是把每次事故写成一条越来越长的提示词警告。

## Workflow 和 Agent 的错误要分别看

固定流程出错和动态调度出错，修法也不同。

如果澄川每次都在销售审批之前缺少资料冲突检查，这是 Workflow 的顺序问题。团队应该调整流程节点，并补异常分支。

如果一个开放式检索 Agent 已经拥有正确工具，却经常在第一条弱证据后停止搜索，则可能是 Agent 的停止策略、预算或工具选择问题。这里才需要调整 Planner、Agent Policy、Skill 或上下文。

把两类问题混在一起，会出现一种常见现象：固定流程本来就少一步，团队却不断让模型“多想一想”。

## 一次失败应该产生至少一个可验证改动

复盘如果只留下“加强监控”“优化提示词”“提高稳定性”，下一轮很难判断是否真的完成。

澄川要求高影响失败至少产生一项有主人的系统改动，并说明怎样验证。

例如：

| 失败 | 改动 | Owner | 验证方式 |
|---|---|---|---|
| `T-018` 重复写入 | `unknown` 状态禁止创建新幂等键 | 技术负责人 | 故障注入 + 历史回归 |
| v2.1 过期资料被引用 | 资料目录增加失效时间与发布检查 | 内容负责人 | 上下文冲突样本 |
| 完整会议转写进入普通日志 | 改为轨迹字段白名单 | 数据/技术负责人 | 日志扫描 + 权限测试 |
| 渠道字段语义误用 | 新建本地字段语义与来源登记 | 渠道业务负责人 | 本地语义评审 + 场景样本 |

改动可以很小，但必须有明确终点。

## Eval 是学习闭环的闸门，不只是成绩单

失败进入资产以后，还没有完成学习。

任何 Rule、Skill、Workflow、Ontology 或 Tool 变化，都可能修好一类问题，同时破坏另一类任务。因此改动后必须回到评估。

澄川把评估分成两层：

第一层是针对本次改动的定向回归。例如修改资料有效期逻辑，就先跑资料过期、资料冲突和正常资料样本。

第二层是按风险决定是否重跑更大的回归集。状态机、权限、Action 和环境写入变化通常需要完整高风险回归；一段只影响内部文案格式的 Skill 修改，可以使用更窄的语义评估。

最终发布记录必须把资产版本和评估结果连在一起。团队不能只说“Ontology 更新了”或“Skill 升级了”，还要知道新版本通过了哪些任务，哪些边界仍未验证。

## Trace 不是 Memory，失败记录也不是自动学习

运行轨迹可以成为学习材料，但不能默认直接写入 Agent Memory。

一条失败 Trace 可能包含错误判断、敏感上下文、临时配置和已经失效的资料。若系统把它原样加入长期记忆，下一次反而会把事故当成经验复用。

因此澄川把“运行证据”和“可复用知识”分开：

```text
Trace / Incident
  ↓
分析与分类
  ↓
专家或 Owner 确认
  ↓
形成 Knowledge / Rule / Skill / Workflow / Ontology 改动
  ↓
Eval
  ↓
发布为可复用资产
```

中间的确认和评估不能省掉。

即使以后系统能自动发现失败模式、生成 Skill 草案或提出 Ontology 修改，它仍然只是在加速这条流程。什么能够进入组织共享资产，仍需要明确的证据和治理门槛。

## 组织开始拥有“从执行中学习”的能力

到这里，第 10 章所说的组织资产不再只是项目交付包。

一个成熟些的资产层会同时包含：

- Business Capability 与场景说明；
- Knowledge Asset、Owner、Freshness 与 Provenance；
- Domain Model / Ontology；
- Rule / Function / Action；
- Skill / Workflow；
- Tool Adapter 与 Runtime Contract；
- Trace Schema、Failure Taxonomy 与 Incident；
- Eval Dataset、Rubric 与 Release Gate。

这些资产不是越多越好。它们的共同要求是有人负责、能够版本化、知道适用范围，并能被运行或评估重新验证。

组织能力因此不再等于“很多团队都做了 Agent”。更重要的是，第二个项目可以复用前一个项目已经验证过的知识、语义、动作、运行约束和失败经验，不必从聊天记录和原作者记忆重新开始。

## 最终形成的不是自动自我改写，而是受治理的改进闭环

澄川现在的学习路径可以画成：

```text
真实任务执行
    ↓
Trace + Environment Result
    ↓
Eval / Incident Review
    ↓
Failure Classification
    ↓
Knowledge / Ontology / Rule / Skill / Workflow / Runtime 改动
    ↓
Regression Eval
    ↓
Versioned Release
    ↓
新的真实任务
```

这条闭环允许一部分步骤逐渐自动化，例如聚类失败、建议新增回归样本、生成 Skill 草案。但系统不需要为了“自我进化”而拥有修改所有生产资产的权限。

可靠的组织学习更像软件工程和知识管理的结合：运行留下证据，证据触发具体改动，改动经过验证再进入下一次运行。

第 11 章的毕业项目会把整条链重新收回来。一个完整作品不只要展示“Agent 能做什么”，还要说明它服务什么业务结果、如何理解业务世界、怎样执行和受控，以及发生失败后，证据会怎样回到系统和组织资产。
